# บันทึกพัฒนา Login และ UC01 — 4 พฤศจิกายน 2569

สถานะล่าสุดตาม H25: Login และ UC01–UC10 เปิดใช้งานแล้ว ผ่าน MySQL/JDBC/MVC/Security 71 กรณี และ Chrome 37 จุดตรวจ ส่วน H22–H24 เป็นประวัติการพัฒนาและย้ายโปรแกรม

ผู้ใช้ให้เริ่มพัฒนาต่อหลังอนุมัติและปรับแบบ H21 แล้ว เป้าหมายรอบนี้คือเปิดโปรแกรมในคอมเครื่องเดียว ล็อกอินด้วยบัญชีแยก และค้นหาห้องว่างจาก MySQL จริงได้

กรณี MySQL ครอบคลุม: หน้าต้องล็อกอินและ CSRF, รหัสผ่านผิด/บัญชีไม่พบ/SQL injection, เปลี่ยน session ID และออกจากระบบ, ห้อง/เตียง/ราคา, ช่วงจองทับกันหกแบบรวมวันต่อกัน, รวมหลายแถวของห้องเดียว, CANCELLED/CHECKED_IN/ACTIVE, ห้องไม่พร้อมใช้งาน, ห้องสกปรกหรือมีผู้พักวันนี้แต่วันอนาคตว่าง, ค้นซ้ำหลังฐานเปลี่ยน, จำนวนที่ขาด, ค่าค้นหาไม่ถูกต้องเจ็ดแบบ, ผลว่างเทียบกับโหลดล้มเหลว, ไม่เขียนข้อมูลจากการค้นหา, จำนวนตาราง/ฟิลด์/FK, ผู้รับที่ยังไม่ครบ, คืนพักก่อนวันที่เข้าจริง และคีย์คู่/คืนที่ชำระซ้ำ

SQL ที่ใช้ผ่านโปรแกรมรอบนี้คือ queryAUTH_1 กับ queryUC01_1 มีการใช้ generated keys และ constraints ผ่าน fixture เพิ่มเติม แต่ยังไม่ใช่ผลทดสอบทุกคำสั่งของ UC02–UC10 การ rollback ของ fixture ไม่ใช่หลักฐานว่าธุรกรรมบันทึกของ UC ที่ยังไม่พัฒนาทำงานแล้ว

ผล JUnit อยู่ที่ target/surefire-reports ส่วน log Maven อยู่ใน .runtime/maven-test.log หลักฐาน Chrome และภาพอยู่ข้างไฟล์นี้ ไม่คัดลอกรหัสผ่านจาก local-settings หรือ demo-accounts ลงเอกสาร

## H23 — เพิ่ม UC02 หลังผู้ใช้ให้ทำต่อ

ผู้ใช้บอก “ทำต่อๆ” ระหว่างเก็บงานส่วนแรก จึงต่อ UC02 จากผลค้นหา UC01 โดยยึดข้อสรุปเดิมว่าเพิ่ม/ลดอยู่ในแก้ไข และยกเลิกหมายถึงไม่เข้าพักเลย

- เลือกหลายห้องกับวันพักจาก UC01 ไปสร้างการจอง ค้นด้วยรหัส/ชื่อ/โทรศัพท์ เปิดดูรายละเอียด แก้ไขชื่อ โทร ห้อง และวันพัก เพิ่มห้องหรือติ๊กห้องที่ลดออกได้
- ห้ามแก้ CHECKED_IN หรือรายการของ booking อื่น ต้องส่งรายการ BOOKED ที่ยังแก้ได้ครบเพื่อกันแบบฟอร์มเก่าเขียนทับข้อมูลใหม่ รายการที่ลดออกเปลี่ยนเป็น CANCELLED และไม่ลบประวัติ ถ้าลดทุกห้องจนไม่เข้าพักเลยให้ใช้ยกเลิกทั้งหมด
- CANCEL ยกเลิก BOOKED ทั้งหมดของการจอง ถ้ามี CHECKED_IN จะไม่ให้ยกเลิกทั้งการจอง เก็บ booking_history ก่อนทั้ง EDIT และ CANCEL พร้อมค่าก่อนแก้และรหัสพนักงานที่ทำรายการ ส่วน staff_id ผู้รับจองเดิมไม่เขียนทับ
- Controller ใช้ TransactionTemplate แบบ READ_COMMITTED ล็อกรายการจองเดิมและห้องที่เกี่ยวข้องเรียงตามรหัส โหลดข้อมูลใหม่และตรวจห้องว่างซ้ำภายใน transaction จากนั้นเขียน → อ่าน queryUC02_3 → map → commit แล้วจึง applySavedBooking การตรวจแรกจากแบบฟอร์มไม่แทนการตรวจซ้ำภายใน transaction
- การสร้างใช้ generated keys รายการหัว/ห้องอยู่ในธุรกรรมเดียว การเขียนล้มเหลวหรืออ่านกลับไม่ได้ไม่ทิ้ง booking บางส่วนไว้ กรณี concurrent จองห้องเดียวกันสองคำขอ ผ่านได้หนึ่งคำขอ อีกคำขอได้ข้อขัดแย้ง ไม่เกิดจองซ้ำ
- ทดสอบจริงเพิ่ม 16 กรณี รวมทั้งหมด 44 กรณีผ่าน ไม่มี failure/error/skip ครอบคลุม create/read/search/edit/add/remove/cancel-all, พนักงานอีกคนแก้ต่อ, ประวัติก่อนแก้, CHECKED_IN/foreign item, malformed input, ห้องไม่พร้อม/ทับวัน, read-back failure rollback, วันต่อกัน และ concurrency
- Chrome เพิ่ม 8 กรณีบน instance พอร์ต 8081 ที่ชี้ hotel_frontdesk_test ครอบคลุม UC01 → สร้างสองห้อง → ค้นซ้ำเหลือ 25 Standard → ลดห้องและเพิ่ม Deluxe → ยกเลิกทั้งหมด → Standard กลับเป็น 27 → ยังค้นประวัติได้ ตรวจ DB ก่อน cleanup ว่ามีสาม item ที่เป็น CANCELLED และประวัติ EDIT/CANCEL อย่างละหนึ่ง จากนั้นลบเฉพาะ booking สมมติที่ตัวทดสอบสร้าง ไม่แตะฐานใช้งาน hotel_frontdesk
- ปรับเมนูและหน้า UC01 ให้เลือกห้องไป UC02 มีหน้า booking list/create/detail/edit/cancel-confirm แบบฟอร์มเพิ่มแถวใช้ JavaScript ในเครื่อง บนจอแคบเมนูขึ้นบรรทัดใหม่เพื่อไม่ให้ทั้งหน้าล้น

เอกสารที่ยังต้องประสานตามโปรแกรม: Sequence/Collaboration UC02 ขั้น 9 ต้องยกเลิกทั้งหมด, Query queryUC02_2 และ DD_booking_history ต้องระบุ history ทั้ง EDIT/CANCEL, UPDATE item แก้ได้เฉพาะ BOOKED และต้องอธิบายการ lock/reload/READ_COMMITTED ภายใน transaction รายละเอียดนี้ยังไม่ถูกเขียนทับไฟล์ออกแบบที่เพื่อนกำลังตรวจ และไม่ปิด R02 ว่าตรงกันทุกไฟล์แล้ว

UC03–UC10 ยังไม่พัฒนา ผลรอบนี้ไม่รับรองการบันทึกรับเงิน/เช็คอิน/รายงานที่ยังไม่มีโค้ด และไม่ใช่ผลตรวจยืนยันของเพื่อน

## H24 — ย้ายโปรแกรมเข้า Project_new_ver ตามคำขอ

ย้าย hotel-app ทั้งโฟลเดอร์จาก Project เข้า Project_new_ver รวม source, JAR, MySQL, ข้อมูลเดิม, cache และบัญชีทดสอบ ใช้ Project_new_ver/hotel-app เป็นโค้ดหลักที่เดียว ปิดแอป/ฐานข้อมูลและรอ process ออกก่อนย้าย ตรวจ hash ทุกไฟล์ก่อน–หลังย้าย แล้วปรับลิงก์และพาธของเครื่องมือที่อ้างโฟลเดอร์เดิม สคริปต์เปิดโปรแกรมสร้าง mysql.ini จากตำแหน่งใหม่ให้โดยไม่ล้างฐานหรือเปลี่ยนรหัสผ่าน

รายการทดสอบเดิม 44 MySQL / 17 Chrome และงาน UC02 ที่ยังต้องประสานเอกสารยังคงเดิม การย้ายโฟลเดอร์ไม่เพิ่มขอบเขต UC

ผลตรวจหลังย้าย H24: ทดสอบ MySQL/JDBC/MVC 44 กรณีผ่านทั้งหมด และทดสอบ Chrome ซ้ำ 9 กรณีผ่าน เปิดโปรแกรมที่ http://127.0.0.1:8080 ได้ตามเดิม ข้อมูลหลักยังมี 41 ห้อง/3 ประเภท/2 บัญชี ส่วน booking/stay/payment ยังเป็น 0 รหัสผ่านและไฟล์ตั้งค่าส่วนตัวตรงกับก่อนย้าย โฟลเดอร์ Project/hotel-app เดิมไม่มีแล้ว หลักฐานอยู่ใน app_relocation_20261104/verification-result.json
